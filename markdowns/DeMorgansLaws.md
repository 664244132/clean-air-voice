# 🚨 Project Rules: De Morgan's Laws & Early Return

**สถานะ:** บังคับใช้ (Mandatory)
**เป้าหมาย:** บังคับให้ AI Agents และนักพัฒนาทุกคนในโปรเจคนี้ เขียนโค้ดที่คลีน อ่านง่าย โครงสร้างแบนราบ (Flat) และไม่มีการปฏิเสธซ้อนกัน

## 📜 กฎข้อบังคับที่ 1: De Morgan's Laws (การจัดการเงื่อนไข)

**ห้าม**เขียนเงื่อนไขที่มีการใช้ NOT (`!`) ครอบวงเล็บของนิพจน์ทางตรรกศาสตร์ (เช่น `!(A && B)` หรือ `!(A || B)`) หากพบโครงสร้างแบบนี้ในโค้ด **คุณต้องทำการ Refactor โดยใช้กฎของ De Morgan ทันที**

### กฎย่อย 1.1: ห้ามใช้ `!(A && B)`
เมื่อพบเงื่อนไขรูปแบบ `!(A && B)` **ต้องแปลงเป็น** `!A || !B` เสมอ

### กฎย่อย 1.2: ห้ามใช้ `!(A || B)`
เมื่อพบเงื่อนไขรูปแบบ `!(A || B)` **ต้องแปลงเป็น** `!A && !B` เสมอ

> [!IMPORTANT]
> **คำสั่งสำหรับ AI Agents**: ก่อนทำการ Submit โค้ด, เสนอแนวทางแก้ไข, หรือ Refactor โค้ด ให้สแกนเงื่อนไข `if-else` ทุกครั้ง หากพบการละเมิดกฎนี้ ให้จัดการแปลง (Distribute) เครื่องหมาย `!` เข้าไปข้างในวงเล็บโดยอัตโนมัติ

### 🛠 กฎการกลับเครื่องหมาย (Operator Inversion)
เวลาที่กระจาย `!` เข้าไปหาตัวแปรหรือนิพจน์ **คุณต้องกลับด้านเครื่องหมายเปรียบเทียบ** ตามกฎตายตัวด้านล่างนี้:

| เมื่อเจอเครื่องหมายนี้... | ...ต้องถูกเปลี่ยนเป็นสิ่งนี้ |
|---|---|
| `==` (เท่ากับ) | `!=` (ไม่เท่ากับ) |
| `!=` (ไม่เท่ากับ) | `==` (เท่ากับ) |
| `>` (มากกว่า) | `<=` (น้อยกว่าหรือเท่ากับ) |
| `<` (น้อยกว่า) | `>=` (มากกว่าหรือเท่ากับ) |
| `>=` (มากกว่าหรือเท่ากับ) | `<` (น้อยกว่า) |
| `<=` (น้อยกว่าหรือเท่ากับ) | `>` (มากกว่า) |

## 🚀 กฎข้อบังคับที่ 2: Early Return Pattern (การจัดการ Flow)

**Early Return** (บางครั้งใช้ร่วมกับแนวคิด Guard Clause) คือเทคนิคการสั่ง `return` เพื่อออกจากฟังก์ชันทันทีเมื่อเข้าเงื่อนไขข้อผิดพลาดหรือไม่ตรงเงื่อนไข 

**ห้าม** ใช้ `if-else` ซ้อนทับกันลึกๆ (Nested If / Arrow Code) หรือรอไป `return` ทีเดียวที่บรรทัดสุดท้าย หากสามารถดักจับข้อผิดพลาดแล้วเด้งออกก่อนได้ **ต้องทำทันที**

### 💻 ตัวอย่างการบังคับใช้ (Enforced Examples)

❌ **ก่อนใช้ Early Return (ห้ามเขียนแบบนี้ - Nesting ลึก อ่านยาก):**
```javascript
function processOrder(user, order) {
    if (user != null) {
        if (order != null) {
            if (user.balance >= order.price) {
                // Happy Path (กระบวนการหลักที่อยากให้ทำ)
                deductBalance(user, order.price);
                completeOrder(order);
                return "Success";
            } else {
                return "เงินไม่พอ";
            }
        } else {
            return "ไม่มีคำสั่งซื้อ";
        }
    } else {
        return "ไม่พบผู้ใช้";
    }
}
```

✅ **หลังใช้ Early Return (ต้องเขียนแบบนี้ - แบนราบ อ่านง่าย):**
```javascript
function processOrder(user, order) {
    // ดักจับกรณีผิดพลาดแล้วรีบ Return ออกไปก่อน (Guard Clauses)
    if (user == null) return "ไม่พบผู้ใช้";
    if (order == null) return "ไม่มีคำสั่งซื้อ";
    if (user.balance < order.price) return "เงินไม่พอ";
    
    // Happy Path (ไม่มีปีกกามาครอบแล้ว)
    deductBalance(user, order.price);
    completeOrder(order);
    return "Success";
}
```

> [!TIP]
> **เคล็ดลับ**: การใช้ **De Morgan's Laws** สามารถช่วยกลับเงื่อนไขให้กลายเป็นรูปแบบที่เหมาะสมกับการทำ **Early Return** ได้อย่างดีเยี่ยม! (เช่น เปลี่ยนจากการเช็คว่า "ถ้าถูกต้องทั้งหมดให้ทำต่อ" ไปเป็น "ถ้ามีข้อใดผิด ให้รีบ Return ออก")

### ⚠️ ข้อควรระวังสำหรับการใช้ Early Return
1. **การจัดการทรัพยากร (Resource Leaks):** หากฟังก์ชันมีการจองทรัพยากร (เช่น เปิดไฟล์ หรือเปิด Database) การรีบ `return` ตรงกลางฟังก์ชันอาจทำให้ลืมปิดทรัพยากร
   * **วิธีแก้:** ในหลายภาษาจะมีคำสั่งอย่าง `try-finally`, `using` (C#), หรือ `defer` (Go) เพื่อบังคับให้คืนทรัพยากรเสมอไม่ว่าจะออกจากฟังก์ชันตอนไหน
2. **หลีกเลี่ยงในฟังก์ชันที่ยาวเกินไป:** ถ้าฟังก์ชันมีความยาวเป็นร้อยบรรทัด และมีจุด `return` กระจายอยู่ 10 จุดทั่วฟังก์ชัน การใช้ Early Return จะกลับกลายเป็นฝันร้ายในการ Debug เพราะจะไม่รู้ว่าฟังก์ชันมันหลุดออกไปที่บรรทัดไหน
   * **วิธีแก้:** Early Return จะทำงานได้ดีเยี่ยมก็ต่อเมื่อคุณเขียนฟังก์ชันให้สั้นและทำหน้าที่เพียงอย่างเดียว (Single Responsibility)

## 💡 เหตุผลที่โปรเจคนี้ต้องบังคับใช้กฎทั้ง 2 ข้อนี้ร่วมกัน

1. **ลดการซ้อนทับของโค้ด (Reduces Nesting):** โค้ดที่ลึกเป็นรูปหัวลูกศร (Arrow Code) จะหายไป ทำให้โค้ดแบนราบ (Flat) และไม่ต้องเลื่อนสายตาเข้าๆ ออกๆ ตามวงเล็บ
2. **เห็น "Happy Path" ชัดเจน:** ตรรกะหลักของฟังก์ชันจะมาอยู่ด้านล่างสุดโดยไม่มี `if` มาครอบ ทำให้อ่านแล้วรู้ทันทีว่าฟังก์ชันมีหน้าที่อะไร
3. **ลดภาระทางสมอง (Lower Cognitive Load):** มนุษย์และ AI ประมวลผลประโยคที่ไม่มีคำปฏิเสธซ้อนกันได้เร็วกว่า และไม่ต้องพยายามจดจำว่า `else` ตัวนี้กำลังจับคู่กับ `if` บรรทัดไหนที่อยู่สูงขึ้นไป
4. **Fail-Fast ทันที:** โปรแกรมจะหยุดทำงานทันทีที่เจอความผิดปกติ ช่วยประหยัดทรัพยากรเครื่องเพราะไม่ต้องประมวลผลโค้ดส่วนอื่นที่ไม่จำเป็น
5. **ง่ายต่อการตรวจสอบ (Reviewability):** โค้ดที่เป็นรูปธรรมและแบนราบ จะทำให้ง่ายต่อการทำ Code Review และควบคุม Test Cases ได้ง่ายขึ้น
